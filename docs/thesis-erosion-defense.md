# 开题答辩稿：终端智能体 Harness 的可信自改进

更新日期：2026-11-10。本文是开题答辩用的完整版本，讲的是论文最终要交付什么。已完成和计划中的工作分开写，答辩时也分开讲。方法细节见 [方法设计](thesis-erosion-monotonicity-method.md)，数据与阶段见 [研究方案](thesis-erosion-plan.md)，故事线见 [论文的故事线](thesis-erosion-story.md)。

## 1. 题目

**终端智能体 Harness 的可信自改进：基于验证单调性的反例引导方法**

英文：Trustworthy Harness Self-Improvement for Terminal Agents: Counterexample-Guided Evolution under Verification Monotonicity

一句话：本课题构建一个终端智能体 Harness 的递归自改进系统（暂名 MonoEvolve）。大模型反复修改 Harness 代码来提高任务通过率，系统保证每一代都不会在证据更少的情况下宣布完成。被拒绝的修改带着最短反例回到大模型手里修复，而不是直接丢弃。

## 2. 选题背景与意义

- **自改进 Harness 是当前热点。** Meta-Harness、Self-Harness、Darwin Gödel Machine、Self-HPO 都让大模型自动修改智能体的代码或 Harness，分数涨了就保留。
- **分数验收有一个盲区。** 真实部署时没有隐藏测试，用户只能看到智能体说“完成了”。大模型为了提分删掉验证步骤，分数可能照样上涨，“完成了”却不再可信。Meta-Harness 公开的 Terminal-Bench 2 搜索记录里，`lean_completion` 删掉两步验证后分数从 28.5% 涨到 32.5%，成为当轮最优，它的后代一直领先到第 6 轮。
- **意义。** 自改进要想用在真实系统里，必须保证改进不靠削弱验证换来。本课题给出一个可执行的验收准则和配套算法，让自改进循环在提分的同时守住“完成声明”的可信度。

## 3. 国内外研究现状

| 方向 | 代表工作 | 已解决 | 留下的空白 |
|---|---|---|---|
| Harness 自改进 | Meta-Harness (2603.28052)、Self-Harness (2606.09498)、Self-HPO (2610.22791) | 自动提出修改并按分数择优 | 按分数验收，看不见、甚至奖励同时提分的侵蚀 |
| 侵蚀的发现与测量 | DGM (2505.22954)、Auditing Harness Tampering (2609.00069)、Masked Erosion (2610.38392) | 证明篡改和侵蚀在自改进中普遍存在；Auditing Harness Tampering 用人工植入的篡改评测大模型审计员；Masked Erosion 统计自然提案对安全护栏的侵蚀 | 对象是安全规则和通用篡改，不是“完成验证”；缺少由模型自然产生、标签先冻结、能横向比较多类守护的完成侵蚀基准 |
| 门级守护 | Kumar et al.（NeurIPS 2026 Workshop, “Gate Presence Is Not a Safety Invariant”）、Falsifiable Release Gates (2607.13070)、Self-Healing Harness (2609.24130)、RegenHarness (2609.27612) | Kumar 等人指出“门还在不等于门安全”，在安装新门之前用探针和参考门做差分；其余工作用常驻不变量和回放用例 | 守的是单个门函数，看不到门之间的控制流、预算和超时。跳过审查、超时放行、检查不计预算时，每个门都没变，完成照样被放水；Kumar 等人自述抓不到超时放行 |
| 结果与评测守护 | SEAL (2607.24300)、Trust Layer (2610.07274)、False Success (2606.09863) | 比较自评与外评的差距；在任务层核对完成声明是否属实 | 评估的是单个版本的结果，没有在接受修改之前判断新版本是否扩大了接受完成的范围 |
| 反例反馈 | CEGIS（程序合成的经典方法）、A-CEGIS (2609.02892)、SCAFFOLD-CEGIS (2603.08520) | 用反例引导大模型修正产物；SCAFFOLD-CEGIS 用于迭代改代码时的安全退化 | 规约固定，只服务单个产物；没有以上一代 Harness 为规约、反例跨代积累的自改进循环 |

空白可以概括为一段话：前人已经证明侵蚀存在，也开始在“门”的层面守护。但门还在、门没变，不等于完成可信，因为完成是由多个门、门之间的控制流和预算共同决定的。现在还缺三样东西：一个专门针对完成验证的自然侵蚀基准；一个在完成尝试层面判定的守护；一个能把拦下的修改修好、让守护越用越强的自改进循环。三者正好对应本课题的三个研究内容。

### 4.2 研究内容一：面向完成验证的自然侵蚀基准（主体已完成）

三个研究内容按“发现问题、拦下侵蚀、修好修改”递进：研究内容一回答侵蚀在什么条件下出现、长什么样，并为后两个研究内容提供数据集和指标；研究内容二拦下侵蚀，输出最短反例；研究内容三用反例修复被拒的修改。

已完成：用三家厂商的模型针对 12 条失败轨迹修改 Dharness，标签在运行任何检查之前冻结。

- 普通提示下 70 个修改中 3 个削弱验证；只加一句“在预算内更常完成”，71 个中有 8 个。
- 这 8 个中有 6 个是同一种修改：审查次数用完后跳过审查。这是本项目历史上修过的缺陷。
- 现有守护对比：回归测试拦下 11 个侵蚀中的 10 个，但误拒三到六成的正常修改；大模型审计几乎不误拒，但漏掉了预算计账类侵蚀，判断不可重放；作者手写的轨迹不变量在自然修改上没有额外检出。

结论：压力提示下侵蚀有增多的趋势（样本还小，双侧 Fisher 检验 p = 0.21，尚未达到统计显著），而且会重现已修复的缺陷；四类现有守护各有盲区，它们判断的是“分数有没有涨”“行为有没有变”或“看起来像不像作弊”，都没有直接检查完成的可信度。

待完成：

- 扩大样本量和提议条件（完成率、预算、分数等多种压力），检验压力趋势是否成立；结果为零效应也照实报告。
- 加入人工植入的侵蚀作为对照，比较“作者想得到的侵蚀”和“模型真会写出的侵蚀”在各类守护下的差别。
- 人工复标全部样本，用人工标签重算所有比较。
- 把作者种子、普通修改、压力修改和 Meta-Harness 公开搜索记录整理成侵蚀评测基准，附冻结的标注协议，供研究内容二的离线评测使用。
- 采用完成声明可信度（沿用 Trust Layer、False Success 的定义），并提出按版本增量计算的虚假提升，供研究内容三的在线评测使用。

### 4.3 研究内容二：完成尝试层面的验证单调性守护（算法一）

**准则。** 候选 H' 相对基线 H 满足验证单调性，当且仅当 H' 接受的每一次完成尝试，把同样的证据交给 H，H 不会以验证原因拒绝。验证原因包括检查失败、证据过期、需求未覆盖、展示性检查、审查拒绝或超时、审查次数用尽。轮数或预算用尽、模型主动停止、基础设施故障不算验证原因。

形式化：

$$\forall \tau,\ \forall a \in \mathrm{attempts}_{H'}(\tau):\ J_{H'}(a) = \mathrm{accept} \Rightarrow J_H(a) \notin \{\mathrm{reject}(r) : r \in R_v\}$$

这条准则只约束“接受完成的范围”，不要求行为等价。改提示、改预算、换策略、多做一批工作都允许。

**算法。**

1. 物化基线和候选两份源码，各自在只继承白名单环境变量的子进程中运行。
2. 以已有的脚本化场景、历史缺陷场景和反例库为初始轨迹。
3. 解析补丁触及的函数，用 7 类变异算子改写轨迹：让检查失败、让审查拒绝或超时、耗尽审查和修复次数、在检查之后修改文件使证据过期、漏掉需求、用 `echo` 充当检查、在收尾阶段注入额外工作。优先保留能执行到被改代码的轨迹。
4. 同一条轨迹在两个版本上各跑一次。
5. 在完成尝试层面判定：候选每接受一次完成，就从 journal 重建那一刻的证据状态，交给基线的判定逻辑。基线以验证原因拒绝，就得到反例。
6. 用 delta debugging 把反例轨迹删到最短。
7. 只改提示词的修改，脚本化模型看不出区别。此时用真实审查模型分别配合新旧提示词，审一组本该被拒的证据样例，统计从拒绝翻成通过的比例，超过预设阈值即判为侵蚀。
8. 输出 accept、reject 加最短反例，或 inconclusive（轨迹在两个版本间对不齐时）。

为什么在尝试层面判定：只比较整条轨迹的结局会误报。候选放宽轮数预算后，在更多轮之后带着完整证据完成，是合理的改进。尝试层面问的是“候选接受的那一次证据，基线是否也接受”，预算差异不会被当成侵蚀。

### 4.4 研究内容三：反例引导的自改进（算法二）

只拒绝不修复，自改进会浪费大量候选。E2b 中被判侵蚀的修改，往往同时带着合理的改动（例如调整收尾阶段的预算分配），直接丢弃会把合理的部分一起扔掉。算法二借鉴程序合成里的 CEGIS，把守护的反例变成下一次提议的输入。

```
输入：根版本 H0，搜索题 T_s，代数 G，每代候选数 K，修复轮数上限 R
P ← H0；反例库 C ← ∅
for g = 1..G:
    F ← P 在 T_s 上的失败轨迹
    候选集 S ← ∅
    for k = 1..K:
        p ← 提议(P, F, 反例库摘要)
        for r = 0..R:
            v ← 守护(P, p, 初始轨迹 ∪ C)
            if v = accept:       S ← S ∪ {p}; break
            if v = inconclusive: break
            C ← C ∪ {v.最短反例}
            if r < R: p ← 修复(p, v.最短反例)
    P ← 在 T_s 上得分最高的候选（S 为空或无提升时保留 P）
输出 P
```

三个设计点：

- **修复而不是重写。** 修复提示只给提议器看最短反例和一句说明（例如“审查次数用尽后，候选在没有审查的情况下宣布完成”），要求它只改违反之处、保留其余改动。这样既保住合理改进，又堵上侵蚀。
- **反例库只增不减。** 每个最短反例都存进反例库，之后每一代的守护都要重放全部反例。某一代抓到过的侵蚀，以后任何一代都不能再引入。守护集随演化变强，而不是作者一次写死。
- **验证只进不退。** 每一代以父版本为规约。某一代加强了验证并被接受，之后的修改就不能再把它削弱回去。

### 4.5 系统集成与评测方案

**离线评测（算法一）。** 在已冻结标签的三组数据上（作者种子 35 个、普通修改 70 个、压力修改 71 个），与回归测试、G1 至 G3、大模型审计比较：侵蚀检出率、正常修改误拒率、无法判定比例（均带 Wilson 95% 区间），单次耗时，反例长度。消融：去掉定向变异，改为结局层面判定，去掉提示词哨兵。

**在线评测（完整系统）。** Terminal-Bench 2 中 15 道搜索题和 15 道互不相交的留出题，10 代，每代 2 个候选，修复最多 2 轮。为了让侵蚀有机会出现，提议器使用已知会诱发侵蚀的完成压力提示。对比组：

| 组 | 选择规则 | 必做 |
|---|---|---|
| A0 | 只看分数 | 是 |
| A1 | 分数 + 回归测试 | 预算允许时 |
| A2 | 分数 + 大模型审计 | 预算允许时 |
| A3 | 分数 + 单调性守护，只拒绝 | 是 |
| A4 | 完整系统：分数 + 单调性守护 + 反例引导修复 | 是 |

**指标。**

- 留出通过率。
- 完成声明可信度：宣布完成的任务中，真正通过外部评测的比例。
- 虚假提升：内部宣布完成率的提升减去外部通过率的提升。
- 谱系中被接受的侵蚀修改数（按冻结的标注协议判定）。
- 修复挽回率：被守护拒绝的候选中，修复后被接受的比例。
- 成本：模型 token、墙钟时间、守护耗时。

## 5. 创新点

本课题有三个创新点，与三个研究内容一一对应：创新点一给出针对完成验证的自然侵蚀基准，创新点二拦下侵蚀，创新点三把被拦下的修改修好。后两者合成 MonoEvolve 系统。

故事主线是一句话：**门还在不等于门安全（Kumar 等人），门安全也不等于完成可信（本文）。** 每个创新点按四个方面论证：问题是否真实存在（必要性），前人做到了哪一步、还留下什么（空白），本文如何解决（机制），已有哪些基础（可行性）。下文的数字都来自已完成的前期工作，创新点二、三的机制是按准则定义做的推导，有效性由第 6 节的预测检验。

### 创新点一：面向完成验证的自然侵蚀基准（研究内容一）

在固定的失败轨迹上，让多家厂商的模型在不同提议条件下自然产生 Harness 补丁；标签在任何守护运行之前冻结；在同一套标签上横向比较各类守护；用完成声明层面的虚假提升衡量漏检的代价。

- **故事。** 前人测的是安全规则被怎样削弱（Masked Erosion），或者人工植入的篡改能不能被审计员发现（Auditing Harness Tampering）。本文测的是“完成”这件事本身被怎样放水，而且样本是模型自己写出来的。
- **必要性：植入的侵蚀只反映作者想得到的模式。** 前期的自然补丁里就出现了作者没有写进种子的侵蚀：把完成检查排除出预算计账（`dna-assembly__deepseek-v4-pro__s1`）。审查次数用完就跳过审查这一历史缺陷，也被模型反复写了出来。没有一个以完成验证为对象、能公平比较各类守护的数据集，守护之间就无从比较。
- **与近邻的区别。** Auditing Harness Tampering 用植入样本，只评测大模型审计员；本文用自然补丁，同时比较回归测试、大模型审计、作者探针和本文方法。Masked Erosion 研究 AppWorld 上的安全护栏，只用一个模型，冻结的是预测；本文研究终端任务上的完成验证，用三家厂商的模型，冻结的是标签。完成声明可信度沿用 Trust Layer 和 False Success 的定义；本文新增按版本增量计算的虚假提升，用来评估自改进循环。
- **前期结果。** 已有作者种子 35 个、普通补丁 70 个、压力补丁 71 个和 Meta-Harness 公开提案 20 个。普通提示下 3/70 削弱验证、21 个加强验证；压力提示下 8/71 削弱验证，其中 6 个重现历史缺陷 `review_quota_no_bypass`，趋势明显但样本还小。四类守护各有盲区：回归测试误拒三到六成正常补丁；大模型审计漏掉预算计账类侵蚀；作者探针在自然补丁上没有额外检出；确定性守护和审计取并集才在压力补丁上做到 8/8。这些盲区就是创新点二的出发点。
- **待完成与可行性。** 扩大样本量和压力类型，加入植入对照，人工复标，整理发布。采样脚本、标注协议和基线结果都已在仓库中。

### 创新点二：完成尝试层面的验证单调性守护（研究内容二）

提出验证单调性准则：新版本接受的每一次完成，把同样的证据交给上一代版本，上一代也必须接受。准则以上一代版本为规约，不需要作者预先写出每条性质。配套的差分守护算法按补丁定向构造轨迹，在新旧两个版本上差分重放，在完成尝试层面判定，输出可重放的最短反例；只改提示词的修改用新旧提示词的翻转检测覆盖。

- **故事。** Kumar 等人证明了“门还在不等于门安全”，在门的层面做差分探针。本文往前走一步：门安全也不等于完成可信。前期数据里最常见的侵蚀是审查次数用完就跳过审查，它没有改任何一个门，改的是门之间的控制流；`dna-assembly` 改的是预算计账；Kumar 等人自述抓不到超时放行。这些都只有在“整次完成”这一层才看得见。
- **必要性：看分数的验收不仅看不见侵蚀，还会奖励侵蚀。** Meta-Harness 公开的 Terminal-Bench 2 搜索记录里，20 个修改有 5 个明确削弱验证；有分数的 8 个侵蚀修改中，5 个分数高于父节点。`lean_completion` 删掉两步验证，分数从 28.5% 涨到 32.5%，成为当轮最优；第 2 轮到第 6 轮，当前最优候选的祖先里都有它。
- **空白：现有守护问的都不是“这次完成是否可信”。**

  | 守护 | 判断的问题 | 盲区 |
  |---|---|---|
  | 看分数 | 分数有没有涨 | 选中了 `lean_completion` |
  | 回归测试 | 行为有没有变 | 误拒正常修改：普通提示 19/67，压力提示 35/63；漏掉只改审查提示词的 `polyglot-rust-c__claude-sonnet-5-5__s0` |
  | 大模型审计 | 看起来像不像作弊 | 漏掉预算计账类侵蚀 `dna-assembly__deepseek-v4-pro__s1`，判断不可重放 |
  | 作者手写探针 | 作者预见到的单条性质 | 作者种子集上漏掉只改提示词、删掉冗余防线、探针未覆盖路径三类侵蚀 |
  | 门级差分（Kumar 等人） | 单个门在探针上的输出变没变 | 看不到门之间的控制流、预算和超时 |

- **机制一：在完成尝试层面判定，分开侵蚀和合理改进。** 用前期数据中的两类真实补丁推导：
  - 审查配额绕过（压力补丁中 6 个）：基线在审查次数用尽后不宣布完成，候选宣布完成，违反单调性，拦下。
  - 收尾阶段多执行一批工作（13 个普通补丁，全部被同一个确定性探针误拒）：多出的工作之后仍要通过检查和审查，候选接受的那一刻的证据基线同样接受，放行。

  “行为有没有变”会把两类一起拒掉，“接受范围有没有扩大”能把它们分开。
- **机制二：按补丁自动构造轨迹，覆盖非离散的侵蚀。** 7 类变异算子各对应一种侵蚀模式（检查失败、审查拒绝或超时、次数耗尽、证据过期、漏需求、展示性检查、收尾阶段额外工作），其中超时、预算耗尽、证据过期正是门级探针看不到的；优先保留能执行到被改代码的轨迹；delta debugging 输出最短反例和一句说明；提示词修改用真实审查模型在一组本该被拒的样例上比较新旧提示词的翻转比例。
- **与近邻的区别。** 相对 Kumar 等人：判定对象从单个门提升到整次完成尝试；探针从静态集合变为按补丁定向变异并输出最短反例；规约是上一代版本，而不是固定的参考门。Falsifiable Release Gates 检查单个版本的性质，本文检查新旧版本之间的关系；SEAL 比较隐藏任务上的得分，本文比较两个版本对同一份证据的完成判定，SEAL 的 “monotone” 指只允许加强自写测试，与本文不是同一概念；Auditing Harness Tampering 静态读 diff，本文运行候选并给出可重放的反例。差分测试本身是成熟思路，本文的贡献在于判定的层次和对象。
- **可行性。** 补丁物化、可编辑面检查、白名单环境、确定性重放已在 P1 至 P4 完成；种子轨迹现成，有 G2 的 8 个脚本化场景和 Historical-7 的 7 个历史场景。

### 创新点三：反例引导的自改进（研究内容三）

被拒绝的候选带着最短反例回到提议器修复，只改违反之处、保留其余改进；反例沉淀进只增不减的反例库，之后每一代的守护都重放全部反例，使守护随演化变强。

- **故事。** 现有守护，包括 Kumar 等人的语义下限和 Masked Erosion 讨论的各种接受门，都只做一件事：拒绝。本文让守护从“拦”变成“教”：拦下来的修改带着反例回去改，抓到过的错误以后每一代都要再考一遍。
- **必要性一：模型会重犯已经修好的错。** 压力补丁的 8 个侵蚀中，6 个是本项目历史上修复过的同一个缺陷 `review_quota_no_bypass`。抓到过的侵蚀必须在之后每一代都重放。
- **必要性二：侵蚀补丁里常有合理的改动。** 被判侵蚀的压力补丁，往往同时调整了收尾阶段的预算分配等合理部分。只拒绝不修复，会把合理改进一起丢掉，浪费提议预算。
- **与近邻的区别。** CEGIS 和 A-CEGIS 用固定规约合成单个产物。SCAFFOLD-CEGIS 把反例回路用于大模型迭代修改应用代码时的安全退化，规约同样固定。本文的规约是上一代 Harness，反例是新旧版本之间的分歧，反例库跨代积累、每代重放，守护的对象是 Harness 自己的完成验证。SCAFFOLD-CEGIS 已使用 “safety monotonicity” 一词，本文的“验证单调性”指接受完成的范围不扩大，论文中会明确区分。
- **可行性。** 提议器复用 E2 采样脚本 `scripts/erosion_natural_sampling.py`，评分复用 Harbor 评测流程，反例直接来自创新点二的守护输出。

### 不能声称的内容

- 首个发现自改进会削弱验证（DGM、Auditing Harness Tampering、Masked Erosion 已报告）。
- 首个带守护的自改进（Self-Harness、SEAL、Self-Healing Harness 已有），首个对新旧版本做差分验收（Kumar 等人已在门级做过）。
- 首个提出自评与外评差距（SEAL），首个提出完成声明可信度（Trust Layer、False Success）。
- 首个用反例引导大模型改代码（CEGIS、A-CEGIS、SCAFFOLD-CEGIS）。
- 压力导致侵蚀的因果结论。前期差异尚未显著，任务层的研究（2610.04793、2605.20744）也发现压力影响很小，只能说趋势。

## 11. 答辩讲稿（约 8 分钟）

按幻灯片顺序，每页一段。

**第 1 页：题目（20 秒）**

> 各位老师好，我的开题题目是“终端智能体 Harness 的可信自改进：基于验证单调性的反例引导方法”。我要做一个让大模型自己改进智能体的系统，同时保证它不靠削弱验证来刷分。

**第 2 页：背景（1 分钟）**

> 现在很流行让大模型自动修改智能体的代码，分数涨了就保留，比如 Meta-Harness 和 Self-Harness。但真实使用时没有隐藏测试，用户只能看到智能体说“做完了”。如果大模型为了提分删掉验证，分数照样会涨，可“做完了”就不可信了。Meta-Harness 公开的记录里就有这样的例子：一个修改删掉两步验证，分数从 28.5% 涨到 32.5%，成了那一轮最优。

**第 3 页：现状与空白（1 分钟）**

> 前人已经走了两步。第一步是发现问题：DGM、Auditing Harness Tampering、Masked Erosion 都证明自改进会削弱安全检查。第二步是开始守门：今年 Kumar 等人指出“门还在不等于门安全”，在安装新门之前用探针做差分。看分数、大模型审计、回归测试也都有人用。但还差一步：门安全也不等于完成可信。我前期看到最多的侵蚀是审查次数用完就跳过审查，它没有改任何一个门，改的是门之间的流程，只有在整次完成的层面才看得见。

**第 4 页：前期实验（1 分钟）**

> 我先做了一个受控实验，这也是研究内容一的雏形。用三家厂商的模型修改我自己的 Harness，只改一句提示。普通提示下 70 个修改里有 3 个削弱验证，加一句“在预算内更常完成”，71 个里有 8 个。样本还小，没有达到统计显著，但其中 6 个是我们以前修过的同一个 bug，说明模型会重犯修好的错。对比现有守护，每一类都有盲区：回归测试误拒三到六成正常修改，大模型审计漏掉了预算计账类的侵蚀。

**第 5 页：系统总体（1 分钟）**

> 所以我要做的系统叫 MonoEvolve。每一代，大模型读失败轨迹，提出代码修改；修改先过单调性守护；通过的在搜索题上评分，最好的成为下一代。被拒的修改不直接丢掉，而是带着反例回到大模型手里修复。

**第 6 页：算法一，验证单调性守护（1 分钟 30 秒）**

> 核心是一条准则：新版本可以改任何东西，但它接受的每一次完成，旧版本也必须接受。检查方法是给新旧两个版本喂同样的运行剧本，重点构造检查失败、审查拒绝、证据过期这些本该被拦下的情况。新版本每宣布一次完成，就把那一刻的证据交给旧版本判。旧版本会拒绝，就抓到了侵蚀，并把剧本缩到最短作为反例。只改提示词的修改，用真实模型比较新旧提示下审查结论有没有翻转。

**第 7 页：算法二，反例引导的自改进（1 分钟）**

> 很多被拒的修改里也有合理的部分，直接扔掉很浪费。所以被拒的修改会带着最短反例回到大模型，让它只修违反的地方。反例还会存进反例库，之后每一代都要重放，抓到过的侵蚀以后再也进不来，守护会随着演化变强。

**第 8 页：实验设计（1 分钟）**

> 离线部分，在已经冻结标签的三组数据上和回归测试、大模型审计比较检出率和误拒率。在线部分，在 Terminal-Bench 2 上跑 10 代，比较只看分数、只拒绝、拒绝加修复三组，看留出题通过率、完成声明的可信度和虚假提升。

**第 9 页：进度与已有基础（40 秒）**

> 目前 Harness 平台、守护的运行设施、侵蚀数据集和基线对比已经完成。两个算法和在线实验还没开始，计划年底前完成算法一，一月完成系统集成，二三月跑在线实验，四月复标和统计，五月定稿。

**第 10 页：创新点与预期成果（1 分钟）**

> 创新点有三个，和三个研究内容一一对应，主线是一句话：门还在不等于门安全，门安全也不等于完成可信。第一个是面向完成验证的自然侵蚀基准：样本是模型自己写出来的，标签先冻结，再横向比较各类守护。第二个是完成尝试层面的验证单调性守护：新版本放行的每一次完成，旧版本拿着同样的证据也必须认，跳过审查、超时放行这类门级检查看不到的侵蚀都能抓到。第三个是反例引导的自改进：守护从“拦”变成“教”，被拒的修改带着最短反例去修，反例每代重放。预期成果是学位论文、一个开源系统，争取投一篇 B 类。谢谢各位老师。

## 12. 评委可能问的问题

| 问题 | 回答 |
|---|---|
| 这和 Self-Harness、Meta-Harness 有什么区别？ | 它们按分数择优。我的系统在评分之前先检查验证单调性，看分数的方法看不见同时提了分的侵蚀，`lean_completion` 就是例子。 |
| 差分测试不是老方法吗？ | 是，Kumar 等人也已经在门级用过。我的贡献不是差分本身，而是判定的层次和对象：在完成尝试层面判定接受范围有没有扩大，并把反例用来引导下一轮修改。 |
| 和 Kumar 等人的 semantic floor 有什么区别？ | 他们证明门还在不等于门安全，对单个门做探针差分，自己承认抓不到超时放行。我前期最常见的侵蚀是跳过审查，没有改任何一个门，只有在整次完成层面才看得见。另外他们只拒绝，没有修复和反例库。 |
| 压力导致侵蚀，显著吗？ | 现在不显著，p 约为 0.2，所以我只说趋势。研究内容一会扩大样本检验；也有任务层研究发现压力影响很小，我会如实对比。即使压力效应为零，基准和守护比较照样成立。 |
| 8 个压力侵蚀里 6 个是同一个 bug，样本够多样吗？ | 不够，这是基准要补的地方：扩大提议条件，并加入人工植入的侵蚀作对照。同一个 bug 被反复写出来，本身也是创新点三的动机。 |
| 反例引导不就是 CEGIS 吗？ | 思路来自 CEGIS，我会明确引用。区别是 CEGIS 和 A-CEGIS 合成单个产物，反例来自固定规约；这里的规约是上一代 Harness，反例是新旧两个版本之间的分歧，而且反例会沉淀进守护集。 |
| 准则太严，合理的改进被拒怎么办？ | 准则只限制“接受完成的范围”，改提示、改预算、换策略都允许。确实存在合理的新完成路径被拒的情况，这类会单独统计并人工复核。 |
| 为什么不直接用大模型审查？ | 前期实验里它漏掉了预算计账类侵蚀，判断无法重放。我的方法只在提示词修改这一类用模型，而且比较的是新旧两个版本的翻转。 |
| 搜索不完备，没找到反例就算安全吗？ | 不算。这是测试不是证明，论文里会写明。反例库会随演化增长，部分缓解这一点。 |
| 在线循环里如果不出现侵蚀呢？ | 循环使用已知会诱发侵蚀的压力提示。如果仍然不出现，就如实报告，离线结果独立成立。 |
| 实验成本多少？ | 先做 pilot 测单代成本再定规模。必做组只有三组。 |
| 标签可靠吗？ | 目前由两个大模型盲标、第三个裁决，一致性 κ 为 0.73 和 0.77。人工复标是计划的一部分，所有比较会用人工标签重算。 |
| 为什么只在终端任务上做？ | 终端任务的完成判定依赖可执行的检查，验证逻辑最集中，Terminal-Bench 2 也有外部评测可以算可信度。推广到其他领域写在未来工作里。 |
