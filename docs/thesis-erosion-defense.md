# 开题答辩稿：终端智能体 Harness 的可信自改进

更新日期：2026-11-10。本文是开题答辩用的完整版本，讲的是论文最终要交付什么。已完成和计划中的工作分开写，答辩时也分开讲。方法细节见 [方法设计](thesis-erosion-monotonicity-method.md)，数据与阶段见 [研究方案](thesis-erosion-plan.md)，故事线见 [论文的故事线](thesis-erosion-story.md)。

## 1. 题目

**面向终端智能体自改进的完成验证守护与反例引导方法研究**

英文：Research on Completion Verification Guarding and Counterexample-Guided Repair for Self-Improving Terminal Agents

题目按同组学位论文的“面向 X 的 Y 方法研究”格式拟定：“完成验证守护”对应研究内容一、二，“反例引导”对应研究内容三。正文中 Harness 指智能体外层的控制代码（提示词、工具调用、预算与完成判定）。

一句话：本课题构建一个终端智能体 Harness 的递归自改进系统（暂名 MonoEvolve）。大模型反复修改 Harness 代码来提高任务通过率，系统保证每一代都不会在证据更少的情况下宣布完成。被拒绝的修改带着最小反例回到大模型手里修复，而不是直接丢弃。

## 2. 选题背景与意义

- **自改进 Harness 是当前热点。** Meta-Harness、Self-Harness、Darwin Gödel Machine、Self-HPO 都让大模型自动修改智能体的代码或 Harness，分数涨了就保留。
- **分数验收有一个盲区。** 真实部署时没有隐藏测试，用户只能看到智能体说“完成了”。大模型为了提分删掉验证步骤，分数可能照样上涨，“完成了”却不再可信。Meta-Harness 公开的 Terminal-Bench 2 搜索记录里，`lean_completion` 删掉两步验证后分数从 28.5% 涨到 32.5%，成为当轮最优，它的后代一直领先到第 6 轮。
- **意义。** 自改进要想用在真实系统里，必须保证改进不靠削弱验证换来。本课题给出一个可执行的验收准则和配套算法，让自改进循环在提分的同时守住“完成声明”的可信度。

## 3. 国内外研究现状

| 方向 | 代表工作 | 已解决 | 留下的空白 |
|---|---|---|---|
| Harness 自改进 | Meta-Harness (2603.28052)、Self-Harness (2606.09498)、Self-HPO (2610.22791) | 自动提出修改，以任务分数决定去留：Meta-Harness 保留全部候选并维护 Pareto 前沿，Self-Harness 要求两个划分都不退步，Self-HPO 只留严格更优者 | 验收口径都是任务分数，没有一项检查完成声明本身；看不见、甚至奖励同时提分的侵蚀 |
| 侵蚀的发现与测量 | DGM (2505.22954)、Auditing Harness Tampering (2609.00069)、Masked Erosion (2610.38392) | 证明篡改和侵蚀在自改进中普遍存在；Auditing Harness Tampering 用人工植入的篡改评测大模型审计员；Masked Erosion 以受控删除实验表明，冗余的安全防线被删除后，按任务分数验收的接受门无法察觉 | 对象是安全规则和通用篡改，不是“完成验证”；缺少由模型自然产生、标签先冻结、能横向比较多类守护的完成侵蚀基准 |
| 门级守护 | Kumar et al.（NeurIPS 2026 Workshop, “Gate Presence Is Not a Safety Invariant”）、Falsifiable Release Gates (2607.13070)、Self-Healing Harness (2609.24130)、RegenHarness (2609.27612) | Kumar 等人指出“门还在不等于门安全”，在安装新门之前用探针和参考门做差分；其余工作用常驻不变量和回放用例 | 守的是单个门函数，看不到门之间的控制流、预算和超时。跳过审查、超时放行、检查不计预算时，每个门都没变，完成照样被放水；Kumar 等人自述从参考门提取的探针集抓不到超时放行 |
| 结果与评测守护 | SEAL (2607.24300)、Trust Layer (2610.07274)、False Success (2606.09863) | SEAL 用隐藏的候选对现任者审计拒绝明显回退，并提出 verifier–deployment gap；后两篇在任务层核对完成声明是否属实 | 评估的是单个版本的结果，没有在接受修改之前判断新版本是否扩大了接受完成的范围 |
| 反例反馈 | CEGIS（程序合成的经典方法）、A-CEGIS (2609.02892)、SCAFFOLD-CEGIS (2603.08520) | 用反例引导大模型修正产物；SCAFFOLD-CEGIS 用于迭代改代码时的安全退化 | CEGIS 与 A-CEGIS 服务单个产物；SCAFFOLD-CEGIS 已有“拒绝、携带反例重试、积累失败知识库”，但约束的是应用代码的安全属性，失败经验存为自然语言规则；没有以上一代 Harness 的完成判定为规约、可重放反例跨代积累的自改进循环 |

空白可以概括为一段话：前人已经证明侵蚀存在，也开始在“门”的层面守护。但门还在、门没变，不等于完成可信，因为完成是由多个门、门之间的控制流和预算共同决定的。现在还缺三样东西：一条在完成尝试层面判定的验收准则；一种能按补丁自动找出反例的方法，覆盖超时、预算这类门级探针看不到的侵蚀；一个能把拦下的修改修好、让守护越用越强的自改进循环。三者正好对应本课题的三个研究内容。

### 4.2 前期研究：完成验证侵蚀的受控测量（已完成）

这部分是三个研究内容的问题依据和评测数据，不单列为研究内容。

用三家厂商的模型针对 12 条失败轨迹修改 Dharness，标签在运行任何检查之前冻结。

- **压力下侵蚀增多，并重现同一个旧错。** 普通提示下 70 个修改中 3 个削弱验证；只加一句“在预算内更常完成”，71 个中有 8 个（双侧 Fisher 检验 p = 0.21，尚未显著，只作趋势）。这 8 个中 7 个来自同一个模型，6 个是同一种修改：审查次数用完后跳过审查，正是本项目历史上修过的 `review_quota_no_bypass`。压力是诱导条件，不用来估计发生率；Meta-Harness 的迭代搜索里侵蚀为 5/20，单次提议很少侵蚀，更可能来自搜索中的选择压力。
- **现有守护各有盲区，没有一类同时做到全检出和低误拒。** 下表以 11 个侵蚀（普通 3 个、压力 8 个）和 130 个正常补丁（67 + 63）计：

  | 守护 | 侵蚀检出 | 正常补丁误拒（普通 / 压力） | 盲区 |
  |---|---|---|---|
  | 回归测试 | 10/11 | 19/67（28%）/ 35/63（56%） | 断言实现细节，只改审查提示词的侵蚀仍被漏掉 |
  | 大模型审计 | 9/11 | 0/67 / 1/63 | 漏掉预算计账类侵蚀，判断不可重放；标签也来自大模型，可能共享偏差 |
  | 确定性检查（G1+G2+G3） | 9/11 | 19/67 / 23/63 | 漏掉只改审查提示词的侵蚀 |
  | 确定性检查或审计 | 10/11 | 19/67 / 24/63 | 误拒仍高 |

- **两处发现直接给出研究内容一、二的第一批检验点。**
  - 确定性检查与审计的盲区互补：审计漏掉的预算计账类侵蚀由确定性检查拦下，确定性检查漏掉的只改审查提示词的侵蚀由审计拦下。前者对应研究内容二的预算与超时变异，后者对应提示词哨兵。
  - 确定性检查在普通提示下的误拒集中：13 个补丁违反同一个探针，即收尾阶段多执行一批工作而占用验证预留时间。按验证单调性，这类修改之后仍要通过检查，应当被接受。这是研究内容一的预测，将在离线评测中检验，目前还不是结果。

结论：压力提示下侵蚀有增多的趋势，而且会重现已修复的缺陷；现有守护判断的是“分数有没有涨”“行为有没有变”或“看起来像不像作弊”，都没有直接检查完成的可信度。标签目前是大模型临时标签，样本只有 11 个侵蚀，区间很宽。

后续补充，作为研究内容一、二的离线评测数据和研究内容三的在线评测指标：

- 扩大样本量和提议条件（完成率、预算、分数等多种压力），并加入人工植入的侵蚀作为对照。
- 人工复标全部样本，用人工标签重算所有比较。
- 把作者种子、普通修改、压力修改和 Meta-Harness 公开搜索记录整理成带冻结标注协议的评测集。
- 两项在线指标均有出处：完成声明可信度是宣布完成的任务中通过外部评测的比例，与 False Success（2606.09863）刻画的虚假成功率从两侧描述同一问题（后者的分母是失败轨迹），Trust Layer（2610.07274）也核查完成声明是否与实际相符；虚假提升借鉴 SEAL（2607.24300）提出的 verifier–deployment gap，即智能体可见的自评与隐藏真值之差，本文按版本增量计算；SEAL 本身没有“虚假提升”这一指标。

### 4.4 研究内容一：基于验证单调性的 Harness 修改验收方法（算法一的判定部分）

**准则。** 候选 H' 相对基线 H 满足验证单调性，当且仅当 H' 接受的每一次完成尝试，把同样的证据交给 H，H 不会以验证原因拒绝。验证原因包括检查失败、证据过期、需求未覆盖、展示性检查、审查拒绝或超时、审查次数用尽。轮数或预算用尽、模型主动停止、基础设施故障不算验证原因。分类在实现前冻结。

形式化：

$$\forall \tau,\ \forall a \in \mathrm{attempts}_{H'}(\tau):\ J_{H'}(a) = \mathrm{accept} \Rightarrow J_H(a) \notin \{\mathrm{reject}(r) : r \in R_v\}$$

这条准则只约束“接受完成的范围”，不要求行为等价。改提示、改预算、换策略、多做一批工作都允许。

**判定。**

1. 物化基线和候选两份源码，各自在只继承白名单环境变量的子进程中运行。
2. 同一条轨迹在两个版本上各跑一次，记录 journal。
3. 候选每接受一次完成，就从 journal 重建那一刻的证据状态：检查回执、工作 epoch、需求覆盖、审查记录、审查和修复计数。
4. 把证据状态交给基线的完成判定逻辑。基线以验证原因拒绝，就得到反例。
5. 轨迹在两个版本间对不齐，或候选改变了 journal 的记录方式导致无法重建时，判 inconclusive，不计为通过。

为什么在尝试层面判定：只比较整条轨迹的结局会误报。候选放宽轮数预算后，在更多轮之后带着完整证据完成，是合理的改进。尝试层面问的是“候选接受的那一次证据，基线是否也接受”，预算差异不会被当成侵蚀。

### 4.5 研究内容二：基于补丁定向变异的验证侵蚀反例生成方法（算法一的搜索部分）

判定再准，也要先有能触发侵蚀的轨迹。作者手写的场景只覆盖作者想得到的情况，因此轨迹要按补丁自动构造。

1. **种子轨迹。** 已有的 8 个脚本化场景、Historical-7 的 7 个历史场景，以及反例库中的全部反例。
2. **定向变异。** 解析补丁触及的函数，用 7 类变异算子改写轨迹：让检查失败、让审查拒绝或超时、耗尽审查和修复次数、在检查之后修改文件使证据过期、漏掉需求、用 `echo` 充当检查、在收尾阶段注入额外工作。优先保留能执行到被改代码的轨迹（用行覆盖判断），在预算内广度优先扩展。
3. **反例最小化。** 借鉴 Zeller 与 Hildebrandt 的 delta debugging [17]，删除不影响反例的步骤，输出 1-minimal 轨迹（删去任意一步反例即不再复现，但不保证全局最短）和一句说明，例如“审查次数用尽后，候选在没有审查的情况下宣布完成”。
4. **余量探测。** 冗余防线被删除时，其余防线仍会拦下，新旧两版在原轨迹上的判定完全一致，Masked Erosion [5] 称之为被掩蔽的侵蚀。借鉴其 margin-aware 门的思想，本文把余量检查做成差分：对新旧两版同时逐层屏蔽一道完成检查后重放，基线仍拒绝而候选放行，即构成反例。被删掉的防线会在屏蔽其他防线时暴露出来。
5. **提示词哨兵。** 只改提示词的修改，脚本化模型看不出区别。此时受 PROCTOR [16] 金丝雀样例的启发（PROCTOR 的金丝雀是植入的、不可能通过的用例，用来发现作弊或泄漏；翻转比例是本文自己的设计），用真实审查模型分别配合新旧提示词，审一组冻结的本该被拒的证据样例，统计从拒绝翻成通过的比例，超过预设阈值即判为侵蚀。

### 4.6 研究内容三：基于反例引导修复的 Harness 自改进方法（算法二）

只拒绝不修复，自改进会浪费大量候选。E2b 中被判侵蚀的修改，往往同时带着合理的改动（例如调整收尾阶段的预算分配），直接丢弃会把合理的部分一起扔掉。算法二借鉴程序合成里的 CEGIS，把守护的反例变成下一次提议的输入。

```
输入：根版本 H0，搜索题 T_s，代数 G，每代候选数 K，修复轮数上限 R
P ← H0；反例库 C ← ∅
for g = 1..G:
    F ← P 在 T_s 上的失败轨迹
    候选集 S ← ∅
    for k = 1..K:
        p ← 提议(P, F, 反例库摘要)
        for r = 0..R:
            v ← 守护(P, p, 初始轨迹 ∪ C)
            if v = accept:       S ← S ∪ {p}; break
            if v = inconclusive: break
            C ← C ∪ {v.最小反例}
            if r < R: p ← 修复(p, v.最小反例)
    P ← 在 T_s 上得分最高的候选（S 为空或无提升时保留 P）
输出 P
```

三个设计点：

- **修复而不是重写。** 修复提示只给提议器看最小反例和一句说明（例如“审查次数用尽后，候选在没有审查的情况下宣布完成”），要求它只改违反之处、保留其余改动。这样既保住合理改进，又堵上侵蚀。
- **反例库只增不减。** 每个最小反例都存进反例库，之后每一代的守护都要重放全部反例。某一代抓到过的侵蚀，以后任何一代都不能再引入。守护集随演化变强，而不是作者一次写死。
- **验证只进不退。** 每一代以父版本为规约。某一代加强了验证并被接受，之后的修改就不能再把它削弱回去。

### 4.7 系统集成与评测方案

**离线评测（算法一，研究内容一、二）。** 在已冻结标签的三组数据上（作者种子 35 个、普通修改 70 个、压力修改 71 个），与回归测试、G1 至 G3、大模型审计比较：侵蚀检出率、正常修改误拒率、无法判定比例（均带 Wilson 95% 区间），单次耗时，反例长度。消融：去掉定向变异，改为结局层面判定，去掉提示词哨兵。

**在线评测（完整系统）。** Terminal-Bench 2 中 15 道搜索题和 15 道互不相交的留出题，10 代，每代 2 个候选，修复最多 2 轮。为了让侵蚀有机会出现，提议器使用已知会诱发侵蚀的完成压力提示。对比组：

| 组 | 选择规则 | 必做 |
|---|---|---|
| A0 | 只看分数 | 是 |
| A1 | 分数 + 回归测试 | 预算允许时 |
| A2 | 分数 + 大模型审计 | 预算允许时 |
| A3 | 分数 + 单调性守护，只拒绝 | 是 |
| A4 | 完整系统：分数 + 单调性守护 + 反例引导修复 | 是 |

**指标。**

- 留出通过率。
- 完成声明可信度：宣布完成的任务中，真正通过外部评测的比例；与 False Success [15] 的虚假成功率从两侧描述同一问题（后者的分母是失败轨迹），Trust Layer [10] 也核查完成声明。
- 虚假提升：内部宣布完成率的提升减去外部通过率的提升；借鉴 SEAL [7] 的 verifier–deployment gap，按版本增量计算。
- 谱系中被接受的侵蚀修改数（按冻结的标注协议判定）。
- 修复挽回率：被守护拒绝的候选中，修复后被接受的比例。
- 成本：模型 token、墙钟时间、守护耗时。

## 5. 创新点

本课题有三个创新点，与三个研究内容一一对应：创新点一回答“判什么、怎么判”，创新点二回答“反例从哪来”，创新点三回答“拦下之后怎么办”。前两者组成单调性守护，三者合成 MonoEvolve 系统。4.2 节的受控测量是问题依据和评测数据，不单列为创新点。

故事主线是一句话：**门还在不等于门安全（Kumar 等人），门安全也不等于完成可信（本文）。** 每个创新点按四个方面论证：问题是否真实存在（必要性），前人做到了哪一步、还留下什么（空白），本文如何解决（机制），已有哪些基础（可行性）。下文的数字都来自已完成的前期工作，机制部分是按准则定义做的推导，有效性由第 6 节的预测检验。

### 创新点一：完成尝试层面的验证单调性准则（研究内容一）

提出验证单调性准则：新版本接受的每一次完成，把同样的证据交给上一代版本，上一代也必须接受。准则以上一代版本为规约，不需要作者预先写出每条性质；判定在完成尝试层面进行，从 journal 重建证据状态，交给基线的完成判定逻辑。

- **故事。** Kumar 等人证明了“门还在不等于门安全”，在门的层面做差分。本文往前走一步：门安全也不等于完成可信。前期数据里最常见的侵蚀是审查次数用完就跳过审查，它没有改任何一个门，改的是门之间的控制流；`dna-assembly` 改的是预算计账。这些都只有在“整次完成”这一层才看得见。
- **必要性：看分数的验收不仅看不见侵蚀，还会奖励侵蚀。** Meta-Harness 公开的 Terminal-Bench 2 搜索记录里，20 个修改有 5 个明确削弱验证；有分数的 8 个侵蚀修改中，5 个分数高于父节点。`lean_completion` 删掉两步验证，分数从 28.5% 涨到 32.5%，成为当轮最优；第 2 轮到第 6 轮，当前最优候选的祖先里都有它。
- **空白：现有守护问的都不是“这次完成是否可信”。**

  | 守护 | 判断的问题 | 盲区 |
  |---|---|---|
  | 看分数 | 分数有没有涨 | 选中了 `lean_completion` |
  | 回归测试 | 行为有没有变 | 误拒正常修改：普通提示 19/67，压力提示 35/63 |
  | 大模型审计 | 看起来像不像作弊 | 漏掉预算计账类侵蚀 `dna-assembly__deepseek-v4-pro__s1`，判断不可重放 |
  | 门级差分（Kumar 等人） | 单个门在探针上的输出变没变 | 看不到门之间的控制流、预算和超时 |

- **机制：在完成尝试层面判定，分开侵蚀和合理改进。** 用前期数据中的两类真实补丁推导：
  - 审查配额绕过（压力补丁中 6 个）：基线在审查次数用尽后不宣布完成，候选宣布完成，违反单调性，拦下。
  - 收尾阶段多执行一批工作（13 个普通补丁，全部被同一个确定性探针误拒）：多出的工作之后仍要通过检查和审查，候选接受的那一刻的证据基线同样接受，放行。

  “行为有没有变”会把两类一起拒掉，“接受范围有没有扩大”能把它们分开。
- **与近邻的区别。** 相对 Kumar 等人：判定对象从单个门提升到整次完成尝试，规约是上一代版本，而不是固定的参考门。Self-Healing Harness 在同一会话上重放并要求受保护案例不回退，判定者是外部评估器，对象是智能体写的规则；Falsifiable Release Gates 检查单个版本的性质，本文检查新旧版本之间的关系；SEAL 比较隐藏任务上的得分，本文比较两个版本对同一份证据的完成判定，SEAL 的 “monotone” 指只允许加强自写测试，与本文不是同一概念；Auditing Harness Tampering 静态读 diff，本文运行候选并给出可重放的反例。
- **可行性。** 补丁物化、可编辑面检查、白名单环境、确定性重放已在 P1 至 P4 完成；Dharness 的 journal 已记录检查回执、工作 epoch、需求覆盖和审查记录，证据状态可以重建。

### 创新点二：面向完成逻辑的定向轨迹变异与反例最小化（研究内容二）

按补丁触及的代码，用 7 类针对完成逻辑的变异算子自动构造轨迹，找到违反单调性的完成尝试；用 delta debugging 把反例约简到 1-minimal 并附一句说明；只改提示词的修改，用新旧提示词下真实审查模型的翻转检测覆盖。

- **故事。** 判得准还不够，还要找得到反例。Kumar 等人用一组从参考门提取的探针检查新门，自己承认这组探针抓不到超时放行，而且只覆盖一部分面时，优化会转向没被覆盖的面。本文让反例跟着补丁走：补丁改了哪里，就在哪里变异轨迹。
- **必要性：依赖作者预见的检查一定有盲区。** 作者种子集上，手写探针漏掉了三类侵蚀：只改提示词、删掉冗余防线、探针没有覆盖的路径。普通与压力补丁中的 11 个侵蚀，回归测试唯一漏掉的是只改审查提示词的 `polyglot-rust-c__claude-sonnet-5-5__s0`，脚本化模型的回答是固定的，看不到提示词的变化。
- **机制。**
  - 7 类变异算子各对应一种侵蚀模式：检查失败、审查拒绝或超时、次数耗尽、证据过期、漏需求、展示性检查、收尾阶段额外工作。其中超时、预算耗尽、证据过期正是门级探针看不到的非离散侵蚀。
  - 优先保留能执行到被改代码的轨迹，在预算内广度优先扩展。
  - delta debugging 输出最小反例和一句说明，既能重放，也能直接交给提议器修复（创新点三）。
  - 余量探测对新旧两版同时逐层屏蔽完成检查后重放，使“判定一致、余量缩小”的被掩蔽削弱也能产出可重放的反例。
  - 提示词哨兵比较的是基线与候选之间的翻转，而不是单个评审是否可靠。
- **与近邻的区别。** 相对 Kumar 等人：探针从静态集合变为按补丁定向生成，覆盖非离散侵蚀，并输出最小反例。PROCTOR 植入不可能通过的金丝雀用例来发现作弊或泄漏，本文的提示词哨兵只借鉴“用冻结样例检验评审”的思路，翻转比例是本文自己的设计。Masked Erosion 指出按分数验收看不见被掩蔽的删除，并提出要求去掉任一层后仍受保护的 margin-aware 门；本文把这一思想做成新旧两版之间的差分，并输出可重放的反例。变异测试和 delta debugging 都是成熟技术，本文的贡献在于针对智能体完成逻辑的算子与余量探测设计，以及把反例接到验收和修复上。
- **可行性。** 种子轨迹现成，有 8 个脚本化场景（`tests/guard/test_trajectory_invariants.py`）和 Historical-7 的 7 个历史场景；PrefixBench 已有有状态变异框架。

### 创新点三：反例引导的自改进（研究内容三）

被拒绝的候选带着最小反例回到提议器修复，只改违反之处、保留其余改进；反例沉淀进只增不减的反例库，之后每一代的守护都重放全部反例，使守护随演化变强。

- **故事。** 现有守护，包括 Kumar 等人的语义下限和 Masked Erosion 讨论的各种接受门，都只做一件事：拒绝。本文让守护从“拦”变成“教”：拦下来的修改带着反例回去改，抓到过的错误以后每一代都要再考一遍。
- **必要性一：模型会重犯已经修好的错。** 压力补丁的 8 个侵蚀中，6 个是本项目历史上修复过的同一个缺陷 `review_quota_no_bypass`。抓到过的侵蚀必须在之后每一代都重放。
- **必要性二：侵蚀补丁里常有合理的改动。** 被判侵蚀的压力补丁，往往同时调整了收尾阶段的预算分配等合理部分。只拒绝不修复，会把合理改进一起丢掉，浪费提议预算。
- **与近邻的区别。** 现有反例反馈方法作用于被合成或被修改的产物本身：CEGIS 与 A-CEGIS 合成单个程序或正则，SCAFFOLD-CEGIS 在大模型迭代修改应用代码时守护安全属性，失败经验提炼为自然语言规则。本文把反例引导用于守护自改进系统自身的完成判定，据我们检索尚无先例：规约是上一代 Harness 的完成判定，无需人工编写；反例是两代判定在同一轨迹上的分歧，经定向变异找到、约简为可重放的最小轨迹；反例库每代全量重放，守护随演化单调增强。SCAFFOLD-CEGIS 已使用 “safety monotonicity” 一词，本文的“验证单调性”指接受完成的范围不扩大，论文中会明确区分。
- **可行性。** 提议器复用 E2 采样脚本 `scripts/erosion_natural_sampling.py`，评分复用 Harbor 评测流程，反例直接来自创新点一、二组成的守护。

### 不能声称的内容

- 首个发现自改进会削弱验证（DGM、Auditing Harness Tampering、Masked Erosion 已报告）。
- 首个带守护的自改进（Self-Harness、SEAL、Self-Healing Harness 已有），首个对新旧版本做差分验收（Kumar 等人已在门级做过）。
- 首个提出自评与真实评测之差（SEAL 的 verifier–deployment gap），首个提出完成声明可信度（Trust Layer、False Success）。
- 首个用反例引导大模型改代码，首个“拒绝后修复而不丢弃”，首个积累失败库（CEGIS、A-CEGIS、SCAFFOLD-CEGIS）。
- 验证单调性能证明没有侵蚀。它只在观察到的轨迹上比较，会漏掉 Masked Erosion 所说的“判定一致、余量变小”的削弱。
- 压力导致侵蚀的因果结论。前期差异尚未显著，任务层的研究（2610.04793、2605.20744）也发现压力影响很小，只能说趋势。

**第 1 页：封面（约 24 秒）**

> 各位老师好，我是段佳灵，指导教师是桑基韬老师。我的开题题目是《面向终端智能体自改进的完成验证守护与反例引导方法研究》。本课题关注的问题是：在大模型自动改进 Harness 的过程中，如何保证性能提升不以削弱完成验证为代价。

**第 2 页：目录（约 8 秒）**

> 汇报分为四个部分：研究背景与意义、研究现状、研究内容与计划，以及前期工作。

**第 3 页：章节页：研究背景与意义（约 2 秒）**

> 首先介绍研究背景。

**第 4 页：研究背景：智能体 Harness 的自改进（约 32 秒）**

> 终端智能体的表现不仅取决于模型，也取决于模型之外的 Harness，即由提示词、工具调用、预算分配和完成判定组成的控制逻辑。因此，由大模型自动修改 Harness 代码成为近来的研究热点。Meta-Harness、Self-Harness 与 Darwin Gödel Machine 的选择机制各不相同，但验收口径都是任务分数，没有一项检查完成声明本身是否可信。

**第 5 页：研究背景：完成判定是 Harness 可信的底线（约 48 秒）**

> 然而，分数衡量的是任务通过率，而不是“完成了”这句话是否可信。真实部署中没有隐藏测试，可信度只能依靠隔离检查、证据新鲜、需求覆盖和独立审查。Masked Erosion 发现，自改进会悄悄删掉冗余的安全规则，而按分数验收察觉不到。我们发现完成验证也有同样的问题：修改削弱了完成检查，Harness 在证据更少时就宣布完成，我们称之为验证侵蚀。右下图中，Meta-Harness 的候选 lean_completion 删掉两步验证后，通过率从 28.5% 升到 32.5%，成为当轮最优。可见按分数验收不仅看不见侵蚀，还会选中侵蚀。

**第 6 页：研究背景：面临的挑战（约 46 秒）**

> 由此产生三个挑战。其一是验收准则：以分数为准会奖励侵蚀，以行为是否改变为准又会误拒合理改进。其二是反例发现：侵蚀常发生在检查门之间的控制流、预算与超时处理中，依赖作者预见的检查难以覆盖。其三是拒绝之后的处理：模型会重复引入已修复的缺陷，而被拒的修改中也包含合理改动。我们认为，三者的共同根源在于，现有验收衡量的是结果或局部行为，而非完成判定本身。门的存在不等于门的安全，门的安全也不等于完成的可信。

**第 7 页：章节页：研究现状（约 2 秒）**

> 接下来介绍研究现状。

**第 8 页：研究现状：Harness 自改进与验证侵蚀（约 40 秒）**

> 现有工作可归纳为两条主线。一条是 Harness 自改进，均以任务分数择优；另一条是侵蚀现象研究：DGM 在附录中报告了一例绕过幻觉检测的 objective hacking；Auditing Harness Tampering 发现，早期引入的篡改会一直留存到最终版本的祖先链上；Masked Erosion 表明冗余防线被删除后，按分数验收的接受门无法察觉。这些工作确认了侵蚀的普遍性，但研究对象是安全规则与通用篡改，完成判定本身尚缺少系统研究。

**第 9 页：研究现状：自改进的守护方法（约 39 秒）**

> 在守护方法上，基于分数的验收无法识别同时提分的侵蚀；大模型审计不可重放，并存在漏检；回归测试断言实现细节，会误拒合理改进；Kumar 等人将新门与保留的参考门做差分测试，但判定对象是单个门，原作者也指出，其探针集无法覆盖超时放行。因此，研究空白在于：尚无方法在完成尝试层面判定新版本是否放行了旧版本会拒绝的完成，也没有方法用这类反例引导后续自改进。

**第 10 页：研究现状：侵蚀与守护的代表工作（可跳过）（约 15 秒）**

> 本页给出三项代表工作的原图。它们共同说明自改进会削弱检查，但判定依赖静态审计、分数比较或单个门的探针，均未直接检查完成判定本身。

**第 11 页：章节页：研究内容与计划（约 3 秒）**

> 下面介绍研究内容与计划。

**第 12 页：研究框架（约 41 秒）**

> 本课题的总体目标是构建可信的 Harness 自改进系统 MonoEvolve。三项挑战对应三个研究内容：研究内容一是基于验证单调性的修改验收方法，回答如何判定；研究内容二是基于补丁定向变异的反例生成方法，回答反例从何而来；研究内容三是基于反例引导修复的自改进方法，回答拒绝之后如何处理。三者构成闭环：研究内容二借助研究内容一的判定搜索反例，反例交由研究内容三修复，并在后续每一代重放。

**第 13 页：研究内容一：基于验证单调性的 Harness 修改验收方法（约 54 秒）**

> 研究内容一的核心是验证单调性准则：候选版本接受的每一次完成尝试，将相同证据交给上一代版本，上一代不得以验证原因拒绝。该准则以上一代为规约，只约束完成判定的接受范围，不要求行为等价。具体来说，同一条轨迹分别在新旧版本上重放；候选每接受一次完成，就从运行日志重建该时刻的证据，交给基线判定，基线拒绝即构成反例。在这一层面判定，可以区分侵蚀与合理改进：审查耗尽后跳过审查的修改会被拒绝；收尾阶段多执行一批工作、随后仍通过检查的修改会被接受，而后者正是回归测试会误拒的类型。

**第 14 页：研究内容二：基于补丁定向变异的验证侵蚀反例生成方法（约 37 秒）**

> 准则给出了判定标准，还需要找到能触发侵蚀的轨迹。前期发现，手写探针、门级探针和确定性检查各有盲区。为此，我们让反例搜索跟着补丁走：补丁改了哪里，就用 7 类变异算子在哪里改写轨迹，例如审查超时、次数耗尽、证据过期；再用余量探测找出被冗余检查掩盖的削弱；找到的反例用 delta debugging 删到最简。只改提示词的修改，则比较新旧提示词下审查结论的翻转。

**第 15 页：研究内容三：基于反例引导修复的 Harness 自改进方法（约 36 秒）**

> 研究内容三处理拒绝之后的环节。右上图是模型实际写出的补丁：审查次数用完后直接放行。这是本项目修过的历史缺陷，压力实验的 8 个侵蚀补丁中有 6 个重犯了它。因此，我们借鉴 CEGIS：被拒的候选带着最小反例返回提议器，只改违反之处；反例存入反例库，之后每一代都要重放。规约就是上一代 Harness 自身的完成判定，无需人工编写，守护随演化持续增强。

**第 16 页：实验设计与预期结果（约 40 秒）**

> 实验分为离线与在线两部分。离线部分在已冻结标签的三组数据上，与回归测试、作者探针和大模型审计比较侵蚀检出率与误拒率，并进行消融；预测在实现前写定，若结果相反将如实报告。在线部分在 Terminal-Bench 2.0 上运行 10 代，比较仅依据分数、守护仅拒绝、守护加修复三组。两项指标均有出处：完成声明可信度与 False Success 的虚假成功率从两侧刻画同一问题，虚假提升借鉴 SEAL 的 verifier–deployment gap。

## 12. 评委可能问的问题

| 问题 | 回答 |
|---|---|
| 这和 Self-Harness、Meta-Harness 有什么区别？ | 它们的选择机制不同，Meta-Harness 保留全部候选维护 Pareto 前沿，Self-Harness 要求两个划分都不退步，但验收口径都是任务分数。我的系统在评分之前先检查验证单调性，看分数的方法看不见同时提了分的侵蚀，`lean_completion` 就是例子。 |
| 差分测试不是老方法吗？ | 是，Kumar 等人也已经在门级用过。我的贡献不是差分本身，而是判定的层次和对象：在完成尝试层面判定接受范围有没有扩大，并把反例用来引导下一轮修改。 |
| 准则和变异算法不是一回事吗，为什么算两个创新点？ | 它们解决两个独立的问题。准则回答“判什么、怎么判”，变异回答“反例从哪来”。就像 CEGIS 里的验证器和反例生成是两件事：准则再好，找不到触发侵蚀的轨迹也拦不住；轨迹再多，判定不对也会误拒。消融实验会分别去掉两者来检验。 |
| 和 Kumar 等人的 semantic floor 有什么区别？ | 他们证明门还在不等于门安全，对单个门做探针差分，并说明从参考门提取的探针集抓不到超时放行；我只读到摘要，全文以发表版为准。我前期最常见的侵蚀是跳过审查，没有改任何一个门，只有在整次完成层面才看得见。另外他们只拒绝，没有修复和反例库。 |
| 压力导致侵蚀，显著吗？ | 现在不显著，p 约为 0.2，所以我只说趋势。后续会扩大样本检验；也有任务层研究发现压力影响很小，我会如实对比。即使压力效应为零，守护方法和比较照样成立。 |
| 8 个压力侵蚀里 6 个是同一个 bug，样本够多样吗？ | 不够，评测数据会补：扩大提议条件，并加入人工植入的侵蚀作对照。同一个 bug 被反复写出来，本身也是创新点三的动机。 |
| 反例引导不就是 CEGIS 吗？ | 思路来自 CEGIS，我会明确引用。现有反例反馈方法作用于被修改的产物本身，比如 SCAFFOLD-CEGIS 守的是应用代码的安全属性，失败经验存成自然语言规则。本文守的是自改进系统自己的完成判定：规约是上一代 Harness，不用人写；反例是两代判定在同一轨迹上的分歧，可重放，每代全量重放。据我们检索，这是第一个以上一代完成判定为规约的反例引导自改进方法。 |
| Masked Erosion 说冗余防线被删时新旧判定会完全一致，你的单调性检查不也会漏吗？ | 这正是研究内容二设计余量探测的原因。只在原轨迹上比较，确实看不见只让余量变小的削弱；所以我们借鉴 Masked Erosion 的 margin-aware 门，对新旧两版同时逐层屏蔽一道完成检查再重放，基线仍拒、候选放行就是反例，被删掉的冗余防线会在屏蔽其他防线时暴露出来。再加上定向变异专门构造超时、次数耗尽这类边界轨迹，以及反例库每代重放。评测里会植入删除冗余检查的侵蚀，单独统计检出率。 |
| `lean_completion` 只来自一次搜索，能说明问题吗？ | 只作动机。它来自 Meta-Harness 的单次公开搜索，第 2 至第 6 轮的最优候选都源自它。正式结论看前期的受控测量和后续评测。 |
| delta debugging 能保证反例最短吗？ | 不保证全局最短，保证 1-minimal：删去其中任意一步，反例就不再复现。对重放和交给提议器修复来说，这已经足够。 |
| 提示词哨兵和 PROCTOR 是什么关系？ | 受它的金丝雀样例启发。PROCTOR 植入不可能通过的用例来发现作弊；我们用一组冻结的应拒证据，比较新旧提示词下审查从拒绝翻为通过的比例，翻转比例是我们自己的设计。 |
| 反例引导修复具体怎么做？ | 被拒的候选带着 1-minimal 反例和一句说明返回提议器，只改违反之处，保留其余改动，最多修 2 轮；反例进入只增不减的反例库，之后每一代守护都要全量重放。 |
| 准则太严，合理的改进被拒怎么办？ | 准则只限制“接受完成的范围”，改提示、改预算、换策略都允许。确实存在合理的新完成路径被拒的情况，这类会单独统计并人工复核。 |
| 为什么不直接用大模型审查？ | 前期实验里它漏掉了预算计账类侵蚀，判断无法重放。我的方法只在提示词修改这一类用模型，而且比较的是新旧两个版本的翻转。 |
| 搜索不完备，没找到反例就算安全吗？ | 不算。这是测试不是证明，论文里会写明。反例库会随演化增长，部分缓解这一点。 |
| 在线循环里如果不出现侵蚀呢？ | 循环使用已知会诱发侵蚀的压力提示。如果仍然不出现，就如实报告，离线结果独立成立。 |
| 实验成本多少？ | 先做 pilot 测单代成本再定规模。必做组只有三组。 |
| 回归测试是怎么构造的，对比公平吗？ | 回归基线是主干上除守护自身测试外的全部测试，在空补丁上校准后保留 451 个，不是为这批补丁专门写的。它断言实现细节，所以误拒高是预期的；我不把它当稻草人，评测里会报告各档强度下的检出与误拒，并保留大模型审计这个最强基线。 |
| 标签可靠吗？ | 目前由两个大模型盲标、第三个裁决，一致性 κ 为 0.73 和 0.77。人工复标是计划的一部分，所有比较会用人工标签重算。 |
| 为什么只在终端任务上做？ | 终端任务的完成判定依赖可执行的检查，验证逻辑最集中，Terminal-Bench 2 也有外部评测可以算可信度。推广到其他领域写在未来工作里。 |

## 13. 底线

- 讲“本课题将构建”，不讲“我已经做了一个 RSI 系统”。进度页明确说算法和在线实验还没开始。
- 不说新方法已经有效，第 6 节的内容都是预测。
- 不说“首个”。理由见第 5 节。
- 不把 Meta-Harness 的分数变化说成侵蚀有效。那只是一次搜索、19 道题。
- 不把大模型审计与大模型标签的一致说成审计可靠。
