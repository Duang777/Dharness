# 硕士论文开题报告

## 拟定题目

**面向终端智能体的候选状态绑定完成控制与协议感知缺陷验证研究**

英文题目：Candidate-State-Bound Completion Control and Protocol-Aware Failure Validation for Terminal Agents

## 研究摘要

终端智能体可以生成代码、修改文件、运行程序和提交结果，但执行过程中的检查通过并不等于最终任务正确。证据可能来自旧工作状态、另一完成尝试或另一候选，检查程序本身也可能改变待提交产物。研究拟围绕可冻结的终端工作区，建立候选状态、执行证据、完成许可与提交对象之间的一致性条件，并研究如何从真实控制状态构造可重复的协议缺陷测试。

本课题包含两个相互支撑的研究点。第一，研究候选状态绑定的完成事务，使验前冻结、隔离检查、验后授权和提交交接具有明确的状态对应关系。第二，研究协议感知的有状态缺陷验证，从真实轨迹恢复可达前缀，注入结构合法但违反状态语义的事件，并缩减为保留同一违规原因的反例。前者改进完成控制，后者检验实现是否遵守所声明的协议。

研究以 Dharness 为参考实现，复用已有终端运行、历史缺陷和离线分析基础。评价先在同候选、同前缀和同检查条件下分离协议效果，再在同模型和同总预算条件下验证在线影响。预期形成完成协议模型、运行时优化、缺陷验证工具及可复现实验包。课题以计算机硕士论文为主体，按 B 类会议对方法差异、公平对照、外部有效性和证据可追溯性的要求组织研究。

## 研究范围

本次开题以终端智能体完成控制可靠性为研究主线，保留候选状态绑定完成事务和协议感知缺陷验证两个研究模块。基础模型、被测控制器和验证规则在每组实验开始前冻结，自进化及跨轮自主修改 Harness 的实验不纳入本课题。智能体仍可按固定流程修改任务工作区、测试和修复产物。

## 选题依据与研究意义

### 完成声明缺少稳定的状态依据

一个终端任务可能在第一个候选上运行测试，随后修改代码，再依据原来的成功输出宣布完成。另一种情况是完成尝试发生重试，控制器错误地混用不同尝试的回执。即使命令退出码为零，证据也不一定对应最终交付对象。

这类问题需要区分两个判断：控制器是否依据有效证据接受完成，以及产物是否满足任务的真实要求。前者是协议正确性，后者依赖验收标准和外部验证器。研究不能以协议接受替代任务正确，也不能把外部成功替代协议过程的安全性。

### 检查可能改变被检查对象

编译、测试和脚本导入可能生成文件、改写配置或改变目录布局。在活动工作区中运行检查后，最终评分面对的对象可能已经不同于检查开始时的候选。仅从 shell 文本判断命令只读，无法证明不存在副作用。

候选快照可以为每项检查提供相同的起点，并隔离检查副作用。但完整的完成流程还要回答：检查结束后授权的是哪个候选，交接时是否发生变更，外部评分是否确实针对被授权对象。这是拟优化的状态一致性问题。

### 随机模型响应使控制缺陷难以复现

一些完成控制缺陷只在特定预算、阶段、候选和回执组合下出现。重复调用模型未必重现该组合，随机修改 JSON 也可能只触发解析错误，无法到达深层完成状态。因此，需要固定真实前缀，在明确边界注入符合结构的状态故障，并保存可独立执行的反例。

本研究的工程意义是减少错误证据的接受、降低控制缺陷排查成本，并给出协议的适用边界。学术意义在于把完成状态一致性和控制缺陷可重复验证转化为可检验的问题，而非仅报告一个 Agent 的 benchmark 分数。

## 国内外研究现状与课题位置

### 证据授权完成已经有直接相关工作

SpecHarness 将规范编译成义务，依据合格来源的证据提交权威状态，并对工件、输入、验证器、环境和依赖版本进行绑定。[1] ECT 研究契约、回执作用域和封闭重放，并区分轨迹支持与外部真值。[3] Goal-Autopilot 的摘要也描述了持久状态机与执行门禁。[4]

因此，证据门禁、状态机、新鲜度、哈希绑定和失败关闭不能分别作为本课题独立的新颖性主张。与这些工作的比较应落在终端候选的具体执行语义：是否冻结实际候选，检查是否使用彼此独立的副本，验后变更如何处理，提交及评分对象能否与证据一致。

SpecHarness 的附录讨论了在线反馈、轨迹与实际计算量不完全匹配的比较限制。[1] 本课题应先固定候选与检查，隔离控制机制效果，再单独进行在线比较，而不是直接把不同运行的成功率归因于协议。

### 执行验证与测试判别力已有成熟方法

Teaching Agents to Code Reliably 在修复和回退状态上进行差分执行，并用错误补丁变体评价生成测试的判别力。[2] SWT-Bench 通过修复前失败、修复后通过等条件评价测试生成。[8] 这些方法说明执行证据很重要，也说明测试通过不能自动证明语义正确。

本课题主要测试完成控制协议，不能将普通差分验证重新命名为核心贡献。对于检查覆盖不足导致的任务假完成，应独立分析验证器能力，不把它归因于候选绑定机制。

### 状态化故障测试和缩减已有基础

AgentChaos 在模型接口层注入 HTTP 响应故障，包含任务状态、旧响应重放和触发核验。[5] ToolFuzz 主要围绕工具输入及文档一致性构造测试。[6] RESTler 利用请求间依赖生成可达调用序列。[7] Delta Debugging 已研究保持失败的输入缩减。[10]

本课题拟研究的差异是：恢复终端完成控制的真实状态前缀，在模型决策、实际回执、审查和候选证据边界注入语义冲突，并在缩减时保留目标违规与原始来源关系。状态化测试与缩减本身不是创新，必须证明这种协议建模带来更多有效深层测试、更可靠的原因保真或更低的诊断成本。

### 已有技术不能直接转化为新颖性

in-toto 已把材料、产物和执行环节关联为可验证的供应链证据。[9] 本课题可以借鉴其证据来源思想，但不能将产物哈希或执行证据链单独宣称为首次提出。

当前可防守的课题位置是：**针对可冻结终端环境的完成事务一致性，设计可执行的协议约束，并用真实状态前缀与原因保真的缺陷验证检验该实现。** 其新颖性仍须通过最近邻实现比较、独立故障和受控效果证明。

## 研究目标与关键问题

总体目标是改进终端智能体完成控制的可靠性，建立从运行证据到完成许可、再到提交对象的可审计对应关系，并提供不依赖模型重新生成故障的验证方法。

| 研究问题 | 需要回答的问题 | 主要证据 |
| --- | --- | --- |
| Q1：完成事务一致性 | 候选、尝试及工作状态绑定与隔离检查，能否减少状态错配和验后变更导致的协议误接受？ | 固定候选、固定前缀的配对实验及状态性质检查 |
| Q2：在线效用与成本 | 在同模型和同总预算下，协议如何影响任务假完成、错误拒绝、最终成功和运行成本？ | 在线配对运行、单组件消融和独立最终评分 |
| Q3：缺陷验证能力 | 状态前缀建模和原因保真缩减是否优于无状态故障及通用缩减？ | 历史缺陷、未见故障家族及等预算方法对照 |
| Q4：外部有效性 | 方法在满足接口条件的第二个终端 Harness 上，能否保持协议语义及在线效用？ | 适配器能力检查、独立实现和第二 Harness 对照 |

这里的 Q1 至 Q4 是开题研究问题，不替换仓库已经冻结的主实验 RQ1 至 RQ4。新问题需以独立协议登记，避免将新目标混入旧实验结论。

## 拟开展的研究内容与方法

### 研究内容一：候选状态绑定的完成事务

把一次完成尝试表示为契约、候选、检查、回执、控制状态与许可之间的关系。契约在运行开始时固定，模型可以提出操作和完成请求，但不能自行缩小验收义务或构造完成许可。

拟研究以下过程：

1. 在受支持的运行边界冻结一个候选，并记录其身份及适用环境信息。
2. 每项检查从同一候选的独立副本开始，副作用留在副本中。
3. 回执同时对应工作批次、完成尝试、候选、检查程序及实际执行结果。
4. 控制器合取证据覆盖、有效性、预算、阶段和必要审查，生成针对该候选的许可。
5. 在提交交接时核对候选与许可。发生新的写入或身份不一致时，许可失效并进入重新验证或终止。
6. 在支持固定候选评分的适配器中，将被授权候选交给独立评分器。不能固定评分对象的后端，只报告已验证的局部性质，不声称完成全链条一致性。

研究重点是验前、验中和验后的状态关系。为其定义可执行性质：旧工作批次不被接受，旧尝试回执不被接受，跨候选回执不被接受，检查副作用不写回提交候选，过期许可不能授权新候选，以及预算和审查失败不能旁路完成。

现有 Dharness 的候选摘要是对有序 Docker RootFS layer diff ID 的域分隔 SHA-256，不能解释为整个运行时状态的完整哈希。内存、挂载卷、网络服务和外部状态不自动被该摘要覆盖。研究先限定无挂载、可冻结的单容器文件系统任务，外部依赖和不可冻结状态明确标为不支持或单独验证。

拟采用小规模状态模型检查与生产入口执行测试共同验证性质。形式性质只证明声明的状态约束，不证明所有任务的语义正确。

### 研究内容二：协议感知的有状态缺陷验证

从真实 journal 恢复工作批次、阶段、预算、完成尝试和证据来源，识别可以合法到达的注入位置。构造两类事件：解析层故障，以及能进入控制器的结构合法、状态语义冲突事件。分别统计，避免靠大量解析失败抬高检测成绩。

核心故障包含旧证据复用、尝试错配、候选错配、回执次序异常、审查故障旁路和完成预算侵占。后续扩展验后变更和许可交接故障，与第一研究点的性质对应。

每次实验绑定生产源码、原始前缀、注入操作、触发位置和执行结果。协议判据与外部任务评分分别运行。仅修改日志并触发离线判据时，结果称为离线违规；只有在真实生产入口观察到不变量被破坏，才能称为生产控制缺陷。

缩减器删除事件和载荷成员时，保留目标违规、候选与证据的来源关系及可达前置状态。缩减后必须在独立执行中复现同一性质失败，不能只保持任意异常。结果注明所允许的删除操作及局部最小性范围，不宣称全局最小。

为了减轻测试判据与算子共同设计的偏差，增加未用于算子开发的故障家族、自然运行缺陷和第二实现。独立性质判据先冻结，再生成确认性结果。

### 研究内容三：围绕可靠性进行系统优化

优化优先对应研究问题。第一，显式固定可验证的任务义务与允许证据来源，替代默认把整段任务作为单个宽泛 requirement 的验收方式。义务只能来自用户可见要求，不能读取隐藏评分测试。

第二，完善完成许可与候选交接，并记录失效原因。第三，将工作与完成验证的预算统一核算，保证检查、审查和必要修复的开销计入总成本。第四，完善适配器的能力声明，使不满足快照和交接条件的环境明确失败或降为受限模式。

这些是方法实现与效用验证所需的优化，不分别包装为额外创新。性能优化必须在已经证明状态一致性的路径上进行，不通过减少检查或放松拒绝条件取得表面收益。

## 预期创新点及成立条件

### 创新点一：面向终端候选的完成事务一致性方法

拟将候选冻结、隔离取证、状态绑定许可和提交交接统一为可执行的完成事务，研究如何阻止检查污染、证据错配和验后候选变更造成的误接受。

相对版本化证据门禁，待证明的增量在于实际执行候选与提交对象的一致性条件。其成立条件是：同候选、同检查和同预算下，相比独立终点验证和版本证据门禁减少目标协议违规，并维持正确候选的可接受性。仅展示三个绑定字段或若干守卫函数，不能证明该创新成立。

### 创新点二：面向完成协议的可达前缀测试与原因保真缩减

拟把真实控制状态、注入位置和违规原因纳入测试与缩减，形成可以在固定生产版本上重复执行的缺陷反例。

相对接口层故障和通用缩减，待证明的增量在于更高的深层目标到达率、更好的独立缺陷检出能力，或在保留同一原因前提下减少反例规模与定位成本。只有同判据、同预算、同未缩减输入的对照结果支持这些差异，才能将其作为方法贡献。

两项创新都是拟验证主张。当前原型证明可实施，但还不能证明相对最近邻的优势。最大的反驳是已有机制组合，研究必须以机制差异、条件性质和独立实证回应。

## 实验方案与评价方法

### 固定候选实验先隔离控制机制效果

固定正确和错误候选、控制前缀及用户可见检查。独立评分器为候选提供最终正确性标签，隐藏测试不向智能体和完成控制器开放。

配对比较以下方法：模型自报告完成、独立终点重跑、版本化证据门禁以及完整候选事务。各方法使用相同的可见契约和检查集合。版本化门禁优先采用可获得的官方实现；若只能复现论文描述，明确称为重实现基线，记录差异，不宣称已复现原论文成绩。

单组件消融分别关闭工作批次绑定、尝试绑定、候选绑定、检查隔离、覆盖约束、审查或预算保留。每次只改变一个机制。消融仅作为受控实验变体，不通过放宽生产协议实施。

同时保留纯协议故障与检查判别力不足案例。若所有方法都使用不足以判定任务正确的检查，完整协议可能仍接受错误候选，必须如实报告。

### 在线实验衡量实际收益和开销

在相同模型、提示、工具权限、初始任务环境和总预算下，配对比较自报告、独立终点验证与完整协议。模型种子不保证服务完全确定，应配对随机化运行顺序并重复运行。

以两个不同模型家族为计划范围，重复次数在开发集预实验后根据差异稳定性、统计功效及成本确定，并在确认性运行前冻结。验证和审查占用与工作相同的总预算，另报告扣除验证开销后的有效工作量。

每次在线运行由独立评分器评价该方法实际提交的候选，候选变化与控制机制影响共同构成在线总效应。不能将在线轨迹差异解释为固定候选上的机制效应。

### 缺陷验证与缩减进行等预算比较

测试方法比较保留现有 state-aware、random JSON、schema-valid random、接口故障风格及 stateless semantic 五类方法。名称对应具体实现，不假定其中的故障风格基线完整等价于 AgentChaos。

共享 task、attempt、operator 和注入预算，报告结构接受、目标到达、已触发违规、未触发、不可适用、判据等价和基础设施失败。失败或未触发行不从分母静默删除。

缩减比较 no reduction、flat ddmin、HDD 与 source-anchored 方法，共享未缩减输入及独立 witness 判据。统计事件数、载荷规模、规范化字节数、候选评估次数、审计次数、运行成本及原因保真率。失败缩减保留原输入并纳入分母。

### 数据分割和外部有效性

既有 Terminal-Bench 2.0 的 89 题已经产生历史结果，不能将其中的任务宣传为研究者从未接触。28 题 development 与 61 题 test 的既有冻结分割继续服务原协议，未来方法对照产物与开发结果严格分离。

B 类会议版本增加一个未参与当前方法开发的新任务或时间切分 cohort，冻结任务版本、筛选规则、生产源码和判据后采集。不能依据初步结果追加易题、改算子或选择性重跑。

第二 Harness 优先使用固定版本的 mini-swe-agent。先验证其能否提供所需候选、回执和交接语义，再开展在线配对实验。仅有离线 trajectory 映射时，结论限定为语义映射，不称为跨 Harness 在线增益。

### 指标、统计与结论规则

设 A 为方法接受完成，G 为独立评分器认定候选正确。对固定候选分别报告：

- 错误候选接受率，分子为 A 且非 G，分母为全部错误候选。
- 正确候选拒绝率，分子为非 A 且 G，分母为全部正确候选。
- 已接受候选中的错误比例，分子为 A 且非 G，分母为全部已接受候选。
- 协议违规率，分子为独立性质判据确认的违规，分母同时报告全部调度案例及实际触发案例。

在线报告最终成功率、任务假完成、错误拒绝、恢复行为、墙钟、输入输出 token、环境调用、检查次数、审查与容器开销。零分母指标标为不可估计，不能记为零。全拒绝的方法不能因错误候选接受率为零被认定为有效。

统计以 task 为聚类单位，配对报告绝对差及 95% 区间，必要时使用配对检验和多重比较校正。缩减结果以任务簇重采样，避免把同任务大量变体当独立样本。成功率或正确候选接受率的容许下降幅度在开发阶段说明理由并预注册，不在看过结果后调整。

确认性结论须同时满足目标误接受改善、正确完成的可用性要求和可解释的成本。结果未达门槛时，报告未确认或证据不足，并保留负结果。故障未触发、支持任务不足及基础设施问题单独列出。

## 已有基础、可行性与当前缺口

截至本次核查，Dharness 已有控制循环、完成契约、三维新鲜度绑定、隔离检查、完成许可、预算保留和适配器抽象。已有 Historical-7、development campaign、方法对照工具、reducer、统计及表格生成入口，可减少新课题从零搭建的成本。

已提交的 89 题结果为 59 个 reward 1.0、30 个 reward 0 和零 canonical error，包含 85 个实时运行与 4 个回放。85 个实时运行有 10 个内部接受但外部失败，以及 12 个外部通过但内部未完成。它们证明内外判定需要分开评价，不证明新协议优于基线，也不是严格 pass@1。Historical-7 的七组修复前后结果满足冻结预期，支持项目内真实缺陷复现。

本地已有测试运行结果为 549 项通过、2 项因原始 journal 不可用而跳过。确认性主实验所需的九个结果产物尚未生成。统一复现检查返回 partial_invalid，当前运行时摘要与冻结 producer 不一致。采集前必须解决版本绑定，并以新协议记录新增研究设计。不能覆盖旧冻结协议或旧结果来绕过来源检查。

当前主要工作是新增完成事务交接条件、独立性质验证与同候选对照，以及补齐在线与外部有效性证据。该方案不要求训练或更新大模型权重，模型在研究中是外部条件。实验仍需模型调用、容器与原始轨迹存储资源，成本需在开发预实验中实测。

## 研究实施顺序与预期成果

实施按可验收成果推进，不设置日期：

2. 冻结最近邻比较、任务义务和完成事务性质，解决 producer 版本绑定。

4. 在开发数据上检验可行性与成本，随后独立冻结确认性协议、实现及新 cohort。
5. 完成固定候选、在线配对、单组件消融、缺陷测试、缩减及第二 Harness 实验。
6. 依据真实结果写论文、公开可发布复现材料并准备投稿。

预期交付包括：完成事务模型及适用条件，Dharness 优化和第二实现适配，可重复的协议缺陷测试与反例，受控比较及成本结果，完整硕士论文和会议投稿稿。达到投稿研究强度的判断依据是最近邻差异、公平效果证据、独立故障及外部有效性，而非代码量或模块数量。

拟定论文章节为绪论、背景与相关工作、候选状态绑定完成控制、协议感知缺陷验证、系统实现与实验评价、总结与展望。正式章节安排按学校要求及最终结果调整。

## 主要风险与处理方式

最近邻重合是首要风险。如果终端事务差异无法形成可测收益，将方法主张进一步限定为运行一致性条件，或以独立缺陷验证为主线，不继续使用宽泛完成协议创新表述。

评分对象交接依赖后端能力。若 Harbor 或第二 Harness 不能固定被授权候选，需独立实现候选评估路径并报告与官方评分的关系，不能把局部快照检查写成端到端保证。

测试算子与判据可能共同偏向自己的实现。采用独立性质判据、未见故障家族、自然缺陷和第二实现，避免只证明算子能触发自己设计的规则。

验证器覆盖不足和不确定外部状态无法靠哈希解决。明确区分协议证据有效与任务语义充分，将这类案例保留为边界结果。基础设施失败和供应商拒绝也单独分类，不能归因于方法效果。
